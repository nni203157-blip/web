一、产品概述

1.1 项目背景

茶韵山林是一家专营云南古树茶，集生产与销售于一体的茶叶品牌。本项目旨在建设一套以个人消费者为主要服务对象的微信小程序电商系统，通过线上商城实现茶叶商品展示、购物下单、订单履约和售后服务。同时建设运营管理后台，帮助商家管理商品、库存、订单及客户关系。

考虑到茶叶产品还存在企业批量采购、商务礼赠等需求，系统设置独立的企业采购询价入口，并将企业询价数据纳入企业CRM，实现企业客户资料维护、联系人管理及采购跟进。

1.2 产品定位

产品模块核心定位主要职责
C端微信小程序个人消费者购物商城商品浏览、规格选择、购物车、地址管理、零售下单、付款状态、物流查询及售后。
商城运营后台商城日常运营管理工具商品、规格、库存、零售订单、发货、售后、首页内容和用户运营。
个人CRM个人消费者关系管理个人客户档案、零售订单关联、用户标签、备注及服务记录。
企业CRM企业采购客户关系管理企业档案、联系人、采购询价、商务跟进及客户状态维护。

1.3 业务边界与核心原则

核心原则：零售交易与企业采购询价是两条独立业务线，不能相互替代。
业务维度个人零售业务企业采购业务
服务对象个人消费者企业及其采购联系人
业务入口商城首页、商品分类、商品详情独立企业采购/礼赠询价入口
主要行为选购商品并提交零售订单提交采购需求并等待商务跟进
价格机制商城展示的零售售价根据采购数量、定制要求等进一步沟通报价
核心数据零售订单及订单明细企业询价及跟进记录
后台归属商城订单管理企业CRM

个人用户购买茶叶时，不要求填写企业名称、营业执照、采购数量等企业资料，也不需要先提交询价。企业询价不会直接生成普通零售订单。后续如企业确认采购，可在进一步确认交易条件后另行建立相应交易记录。

二、C端个人购物主流程

2.1 购物主流程概览

打开小程序 → 浏览首页 → 进入商品分类 → 查看商品详情 → 选择商品规格 → 加入购物车 → 确认结算 → 填写收货信息 → 提交零售订单 → 模拟付款 → 查看订单 → 商家发货 → 查看物流 → 确认收货

2.2 商品浏览与选择

（1）首页：展示品牌信息、品牌Slogan、商品分类入口、推荐商品、活动内容及企业采购入口。

（2）商品分类：支持按照生普、熟普、古树红茶、古树白茶、茶具和节礼分类浏览商品。

（3）商品详情：展示商品名称、图片、详情介绍、零售价格、规格、库存状态及商品购买入口。

（4）规格选择：用户选择具体商品规格后，系统展示对应售价及可售状态。不同规格可以有不同价格和库存。

（5）购物车：支持添加商品、删除商品、调整购买数量、选择参与结算的商品，并展示对应规格和金额。

2.3 订单结算与提交

用户进入结算页面后，系统展示以下信息：

信息项说明
商品信息商品名称、商品图片、所选规格。
购买数量用户选择的商品数量。
商品金额根据商品规格对应的零售单价和数量计算。
运费按照商家配置的配送规则计算。
优惠金额如后续支持优惠活动，展示实际优惠金额；V1可暂不实现。
应付合计商品金额加运费，再减去适用优惠金额。
收货信息收货人姓名、联系电话及详细收货地址。
重要规则：个人零售结算页面不展示必填企业名称、企业联系人、营业执照、采购需求等企业字段。

提交订单时，系统应以服务端数据为准，重新校验商品是否存在、规格是否有效、当前售价及库存是否满足要求。订单生成时保存商品名称、规格名称、成交单价、购买数量等订单快照，避免商品后续修改影响历史订单。

为避免用户重复点击提交产生多个订单，应设置订单提交幂等机制。同一次提交请求重复到达时，系统应返回原订单结果，而不是重复创建订单。

2.4 支付与订单状态

V1阶段采用明确标注的模拟支付模式，不接入真实收款渠道，不产生真实扣款。

订单状态状态说明主要操作
待付款订单已创建，尚未完成支付。模拟付款、取消订单。
待发货订单已完成付款，等待商家处理发货。查看订单详情。
已发货商家已登记物流信息并完成发货。查看物流、确认收货。
已完成用户确认收货或符合约定的完成条件。查看订单、申请售后。
已取消订单因用户取消或超时等原因终止。查看订单详情。

支付方式边界：模拟支付与真实支付必须区分。模拟支付只能改变演示订单的支付状态，不能被描述为真实支付成功。未来接入微信支付时，应以支付渠道的服务端回调作为真实支付结果依据。

2.5 订单查询、物流与售后

  • 用户可以在个人中心查看自己的订单列表，并按照订单状态筛选。
  • 订单详情展示商品快照、金额、收货地址、订单状态及创建时间。
  • 待付款订单允许用户取消，取消后按照库存规则释放预占库存。
  • 已发货订单展示物流公司、运单号及物流信息。
  • 用户可以确认收货，订单进入已完成状态。
  • 用户可以提交一条售后需求，填写售后问题和说明。
  • 用户可以查看商家的售后处理结果及服务反馈。
订单及地址信息必须按照当前登录用户进行数据隔离。用户只能查询自己的订单、收货地址、物流和售后记录，不能通过修改订单ID等方式读取其他用户的数据。

2.6 个人中心

  • 个人账户信息及用户身份信息。
  • 我的订单及各订单状态入口。
  • 收货地址管理，包括新增、编辑、删除和默认地址设置。
  • 售后记录及处理进度查询。
  • 个人资料与客服服务入口。

三、企业采购询价支流程

3.1 功能定位

企业采购询价是独立于个人商城购物的业务入口，主要服务于企业批量采购、商务礼赠及定制采购需求。企业用户提交采购需求后，系统生成企业询价记录，并进入后台企业CRM，由工作人员负责联系和跟进。

3.2 企业询价流程

小程序首页/企业采购入口 → 进入询价页面 → 填写企业及联系人信息 → 填写采购需求 → 提交询价 → 生成询价记录 → 后台企业CRM → 分配跟进人员 → 商务沟通 → 更新跟进状态

3.3 询价表单规划

字段是否必填说明
企业名称是采购企业的正式名称。
联系人姓名是企业采购或商务联系人员。
联系电话是用于后续商务联系。
采购类型是批量采购、商务礼赠或其他采购需求。
意向商品建议必填选择商品类别或填写意向产品。
预计采购数量是记录大致采购数量及单位。
预算范围选填便于商务人员了解客户预算。
采购说明选填礼盒定制、包装、交付时间等补充要求。

3.4 询价提交后的系统处理

  1. 校验企业名称、联系人、联系电话和采购需求等必填信息。
  2. 生成独立的企业询价编号。
  3. 保存询价提交时间、需求内容及提交来源。
  4. 根据企业名称、联系方式等信息判断是否存在已有企业客户。
  5. 如企业已存在，将询价关联到原企业档案；如不存在，则建立企业客户档案。
  6. 将联系人关联到对应企业，并建立本次询价记录。
  7. 后台工作人员可以查看询价详情、分配跟进人员并记录沟通结果。

3.5 企业询价状态

状态含义
待处理询价已提交，尚未分配或开始处理。
跟进中工作人员已联系客户，正在沟通采购需求。
待客户确认商家已提供初步方案，等待客户反馈。
已达成双方已就采购需求达成合作意向或交易约定。
已关闭客户取消需求、未达成合作或其他原因关闭。

询价状态属于企业商务跟进状态，不与零售订单的待付款、待发货、已完成等交易状态混用。

角色主要职责权限范围

商城运营人员商品和商城内容运营商品管理、分类管理、规格维护、首页内容和推荐商品管理。

CRM/商务人员客户关系维护与企业采购跟进管理个人和企业客户资料、联系人、询价及跟进记录。

4.3 权限管理原则

  • 后台必须通过管理员登录或等效的服务端身份验证进行保护。
  • 不同角色只能访问授权菜单及对应业务数据。
  • 商品价格、规格和库存等重要信息的修改应记录操作人员及时间。
  • 订单发货、售后处理及企业询价状态变更应有操作记录。
  • 涉及用户电话、地址等个人信息时，应按照业务需要控制查看权限。
  • 删除、修改等重要操作应进行必要的二次确认或限制。

五、个人CRM与企业CRM规划

5.1 个人CRM

个人CRM以小程序用户为基础建立唯一的个人客户档案，不应每产生一笔零售订单就新建一个客户。同一用户的多个零售订单应关联同一个个人客户。

资料类型主要内容
基础档案个人客户ID、用户昵称、联系方式、用户身份标识、注册时间。
消费记录关联零售订单、购买商品、订单金额及消费时间。
用户标签新用户、活跃用户、复购用户、礼赠偏好等。
服务记录客服沟通、售后处理、用户反馈和服务备注。

5.2 企业CRM

资料类型主要内容
企业档案企业ID、企业名称、企业联系方式、企业类型、客户状态。
联系人资料联系人ID、姓名、联系电话、职位、所属企业。
采购询价询价编号、采购类型、意向商品、数量、预算和需求说明。
跟进记录跟进人员、沟通时间、沟通内容、跟进结果和下一步计划。

5.3 个人用户与企业联系人的身份关联

关键设计：个人客户和企业联系人是两个独立业务身份，但允许关联到同一个自然人。

例如，张先生平时通过小程序购买个人茶叶，同时又是某公司的采购负责人。此时系统应分别维护：

  • 个人客户档案：记录张先生的个人购物行为、零售订单和个人标签。
  • 企业客户档案：记录其所属企业的名称、采购需求和商务合作情况。
  • 企业联系人档案：记录张先生在企业采购业务中的联系人身份。
  • 身份关联记录：将个人客户与企业联系人关联起来，表明两者属于同一个自然人。

这样既能识别同一个人，又能保留个人消费与企业采购之间的业务边界。企业询价记录归属于企业及对应联系人，不直接混入个人零售订单。

如果没有真实微信登录，可使用测试账号或设备访客会话演示。设备访客身份不能直接冒充微信授权身份。测试账号应有明确的测试身份标记；后续接入微信登录后，再建立真实用户身份映射。

6.2 核心数据字段

6.3 核心数据关联关系

用户 users → 个人客户 personal_customers → 零售订单 retail_orders
商品 products → 商品规格 product_skus → 订单明细 order_items
企业客户 companies → 企业联系人 company_contacts → 企业询价 inquiries
企业询价 inquiries → 商务跟进记录 follow_ups
个人客户 personal_customers ↔ 身份关联 identity_links ↔ 企业联系人 company_contacts

数据设计需要保证以下几点：

  • 一个用户对应一个稳定的个人客户档案，多个订单共享该档案。
  • 一个企业可以拥有多个联系人，一个联系人也可以提交多条询价记录。
  • 个人客户与企业联系人通过身份关联表连接，不直接合并两个客户实体。
  • 零售订单与企业询价使用不同的业务编号、状态和数据表。
  • 订单明细必须保存商品和规格快照，历史订单不能因商品资料变更而改变。
  • 订单必须保存收货信息快照，后续修改地址不能改变已生成订单的收货信息。
  • 支付记录需要区分模拟支付和真实支付，不能混淆两种业务数据。
  • 客户标签及服务记录需要区分个人和企业对象，避免关联错误。

七、关键业务规则与异常情况

7.1 库存与订单规则

  • 商品库存以服务端数据为准，不能仅依赖前端限制购买数量。
  • 提交订单时需要校验可售库存，采用库存预占或原子扣减机制。
  • 并发下单时通过数据库事务、条件更新或库存锁等方式避免超卖。
  • 待付款订单取消或超时关闭后，应释放对应预占库存。
  • 支付成功、取消订单及库存释放应具备一致性控制，避免重复扣减或重复释放。
  • 商品下架后不允许新订单购买，但历史订单仍可以正常查看和履约。

7.2 重复提交与数据一致性

  • 订单提交使用幂等标识，防止网络重试及重复点击创建多个订单。
  • 企业询价提交也应考虑重复点击，避免产生重复询价记录。
  • 订单金额由服务端重新计算，不能信任前端传入的总金额。
  • 商品售价发生变化时，以订单提交时服务端确认的价格保存快照。
  • 订单状态变化需要遵循合法状态流转，不能随意从已完成跳转到待付款。

7.3 客户与权限安全

  • 个人用户只能访问本人订单、地址和售后信息。
  • 企业询价数据按照后台授权进行访问和维护。
  • 企业联系人不能因为电话号码相同就被直接合并，身份关联需要合理确认。
  • 测试访客身份与真实微信授权身份必须区分。
  • 后台涉及重要数据修改时应记录管理员及操作时间。

八、待确认问题

以下3个问题会直接影响产品规则、数据结构和后续实施，需要在正式开发前与业务方确认。

问题一：商品价格、运费及优惠规则如何确定？

目前规划按照商品规格配置零售价，结算时计算商品金额、运费和应付合计。但不同地区是否存在不同运费标准、是否设置包邮门槛、是否存在会员价或优惠活动尚未明确。

待确认：是否需要支持按地区计算运费、满额包邮及优惠活动？

问题二：企业询价提交后，商务跟进与成交如何管理？

目前规划企业询价进入企业CRM，由工作人员进行客户分配、沟通和状态维护。但企业报价、客户确认及最终成交后的交易流程还没有明确规定。

待确认：企业采购是否需要在本期支持报价单、客户确认及企业订单管理，还是仅完成询价和商务跟进？

问题三：小程序用户身份与个人客户资料如何建立？

目前规划允许通过测试账号或设备访客会话完成演示，但正式运营需要确定微信登录、手机号获取和个人客户身份识别方式。此外，同一自然人可能同时是个人消费者和企业采购联系人。

待确认：正式上线是否接入微信授权登录及手机号绑定？企业联系人与个人客户之间是否需要通过手机号验证等方式确认身份关联？

九、项目实施顺序

按照业务依赖关系和核心价值，建议采用分阶段实施方式。优先保证个人消费者能够完成完整购物流程，再完善商城运营能力，随后建设CRM和企业采购询价功能。

阶段实施模块主要交付内容实施目的
第一阶段
基础规划		基础数据与账号体系商品分类、商品、规格、用户身份、管理员角色及权限基础。建立后续模块所依赖的基础数据。
第二阶段
核心商城		C端购物流程首页、商品分类、商品详情、规格选择、购物车、地址、结算、订单及模拟支付。优先实现个人用户完整购物闭环。
第三阶段
运营管理		商城运营后台商品维护、规格库存、订单管理、发货物流、售后和首页内容管理。让商家能够真实管理商城数据和处理订单。
第四阶段
用户运营		个人CRM个人客户档案、订单关联、客户标签、备注和服务记录。沉淀消费者数据，建立持续客户关系。
第五阶段
企业业务		企业CRM与采购询价企业采购入口、询价表单、企业档案、联系人、询价跟进及身份关联。建立独立的企业采购客户管理流程。
第六阶段
完善优化		业务验证与扩展异常流程验证、权限检查、数据一致性检查及后续支付能力扩展。确保业务流程完整、数据可靠并具备扩展能力。

9.1 各阶段验收重点

  • 基础阶段：商品、规格、用户和管理员等基础数据结构明确，权限边界建立。
  • 商城阶段：个人用户无需企业资料即可完成商品选购、下单和模拟付款。
  • 运营阶段：后台修改商品和库存后，客户端能够读取最新数据；订单能够完成发货及物流登记。
  • 个人CRM阶段：同一用户的多笔零售订单能够关联同一个个人客户档案。
  • 企业CRM阶段：企业询价提交后能够进入后台，关联企业和联系人，并记录跟进情况。
  • 完善阶段：重点检查重复提交、库存并发、数据隔离、身份关联和订单状态流转。

十、产品规划总结

本项目以茶韵山林个人消费者电商购物为核心，通过微信小程序提供商品展示、购物车、零售订单、模拟支付、物流查询及售后服务等完整购物体验。运营后台以商品、规格、库存、零售订单和售后管理为主要工作入口，帮助商家完成日常商城运营。

在客户管理方面，系统分别建设个人CRM和企业CRM：个人CRM围绕消费者及其零售订单开展用户运营；企业CRM围绕企业档案、联系人、采购询价和商务跟进开展客户管理。两类客户可以通过身份关联建立联系，但保留各自独立的业务档案。

在业务实施上，优先完成个人零售购物闭环和商城运营管理，再逐步建设客户关系管理及企业采购询价能力。通过明确业务边界、数据关系、角色权限和实施顺序，保证产品既满足当前电商运营需求，也为后续企业采购业务扩展预留空间。
